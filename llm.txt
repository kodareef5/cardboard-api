# Cardboard API

> Render tabletop card scenes from JSON. The browser displays the scene and can export PNG or SVG.

This is a static rendering component. Your application supplies the scene and owns game state, rules, identity, and permissions. No API key, game session, or server-side image endpoint is involved.

Read this text file and the linked docs for discovery. The playground changes its URL to include scene data; it is an interactive editor, not the documentation endpoint.

## Make a request

Use a small JSON configuration. Omitted fields receive defaults: 512 x 512, two players, standard playing cards.

```js
const request = {
  stage: { width: 512, height: 512 },
  players: 2,
  view: { mode: 'player', viewerId: 'p1', playerScope: 'table' }
};
const url = new URL('https://cardboard-api.pages.dev/render.html');
url.hash = new URLSearchParams({ config: JSON.stringify(request) }).toString();
// Open url.href in a browser, or use it as an iframe src.
```

Add `?embed=1` before the fragment for a scene without controls. The URL serves HTML; JavaScript in a browser performs rendering. An HTTP fetch alone does not generate an image.

In browser automation, await `Tabletop.viewer.ready` after navigation. It rejects on rendering or required card-art errors; unavailable avatars use initials. Use `await Tabletop.toPNG(Tabletop.viewer.state)` for a PNG Blob, or `await Tabletop.toSVG(Tabletop.viewer.state)` for SVG text. The page also has download buttons.

## Keep requests and replies small

- Generate URL encoding in code. Explain the readable JSON, not an expanded or encoded scene dump.
- When a user needs a render link, provide one descriptive Markdown link or save it in an artifact. Do not print the raw URL as prose.
- With the browser SDK loaded, `await Tabletop.createRenderURL(request)` produces a compressed link. There is no stored scene ID or short-link service.
- Use artwork URLs or Scryfall IDs, not embedded image bytes. Limits: 64,000 URL characters and 1,000,000 decoded JSON bytes. For larger inputs, use the JavaScript API directly or import JSON in the playground.

## Rendering choices

- Dimensions: 64-4096 pixels per side; 1-8 players. Theme, density, stats, zoom, and zone focus are configurable.
- Extras: reusable glows, single-card focus layouts, and per-position card annotations. Player `counters` are `{name, count}` lists; exact is the default, with compact/capped/scientific options. Use `"infinity"` or decimal strings for huge integers. Read the extras guide for shapes and targeting.
- Player images: `playerScope: 'table'` shows public boards plus that player's hand; `'self'` shows only their zones. `viewerId` identifies the recipient.
- Avatars: optional `player.avatarUrl` uses a centered square cover crop and colored initials on failure. Browser avatar PNG/SVG exports default to 512×512; see the README's Player avatars section.
- Exact cards: provide deck definitions and zone `cardIds`/`count`. Unassigned positions use seeded sample cards.
- MTG: supply a Scryfall printing ID in `scryfallId`; assets have a three-day browser cache. Custom cards accept `artUrl`; remote hosts must allow CORS for export.
- MTG 26 presentation: `theme: 'mtg26'` selects the custom 2–4 player layout, supplied artwork, and 1920×1080 defaults. Set `stage: {width:1080,height:1920}` for Shorts. `view.viewerId` chooses the recipient; `view.mtg` supplies focus, turn, phase, priority, land positions, combat, global stack order, and the background (a named one or `backgroundUrl`). Active player never changes the viewing seat. See MTG26.md for the snapshot contract and layout explorer.
- Visibility controls drawing, not access to the request. Omit private data before sharing a URL; selecting a player does not redact it.
